1Executive Summary

A manual, black-box security assessment was performed against the public-facing web application and API of a cryptocurrency threat-intelligence platform. The platform provides on-chain risk and wallet-intelligence data through a tiered subscription model, sits behind a Cloudflare reverse proxy, and exposes a REST API consumed by its web front end.

The assessment identified two High-severity and one Medium-severity issue. The application was generally well-constructed and no trivial injection, authentication or session-management defects were found; the findings instead cluster around authorization enforcement, resource throttling and network-layer exposure — the areas where business logic and infrastructure configuration, rather than input handling, determine security posture.

  • VA-01 (High, speculative) — the intelligence API returns detailed, apparently paid-tier data to fully unauthenticated requests, inconsistent with the platform's subscription model. Confirmation of the exact tier boundary requires a paid account that was not available during testing; the core issue (sensitive data returned with no authentication) is confirmed.
  • VA-02 (High, confirmed) — the password-reset endpoint enforces its rate limit only at the response layer. Every request continues to queue and deliver a reset email even after the endpoint returns RATE_LIMITED, enabling unbounded email flooding of any registered user.
  • VA-03 (Medium, confirmed) — the origin server IP is discoverable via certificate-transparency logs and accepts direct inbound connections, allowing an attacker to bypass Cloudflare's WAF, rate limiting and bot/DDoS protections entirely by addressing the origin directly.

The unifying theme is that protective controls exist but are not authoritative: a subscription model that may not be enforced server-side, a rate limit that returns an error without stopping the action, and a CDN security layer that can be side-stepped. Each control gives the appearance of protection while a determined requester can act around it. Remediation in Section 6 is correspondingly focused on making each control the actual enforcement point rather than a cosmetic one.

Overall risk rating: HIGH (pre-remediation), driven by VA-01 and VA-02. All findings were reported to the platform owner through a coordinated disclosure process. The assessor invites the owner to report any suspected false positives, particularly on VA-01, where a paid-tier comparison would settle the open question.

2.2 Methodology

Testing followed the OWASP Web Security Testing Guide (WSTG) v4.2 and the OWASP API Security Top 10 (2023), and was structured along PTES phases: reconnaissance, mapping of the application and API surface, manual identification and validation of authorization, rate-limiting and infrastructure weaknesses, non-destructive proof-of-concept development, impact analysis and reporting.

Testing was non-destructive. Password-reset flooding was demonstrated at low volume sufficient to prove the decoupling of the rate-limit response from the email dispatch, and was not sustained. No account takeover was attempted and no third-party infrastructure was tested.

VA-01

Broken Access Control — Paid-Tier Intelligence Data Returned Without Authentication

High
CVSS v3.17.5 (High)
CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N
StatusSpeculative — tier boundary unconfirmed without a paid account
CWECWE-306 (Missing Authentication for Critical Function); CWE-285 (Improper Authorization)
OWASP Top 10 2021A01:2021 — Broken Access Control
OWASP API 2023API1 — Broken Object Level Authorization; API5 — Broken Function Level Authorization
Affected assetGET /api/<intel-report> (premium intelligence endpoint; path generalized)

Why this is reported as speculative. The endpoint returns detailed intelligence data to unauthenticated requests, which is inconsistent with the platform's paid subscription model. Whether this is a genuine access-control bypass or intended behaviour cannot be confirmed without a paid-tier account for direct response comparison, or visibility into server-side tier-enforcement logic. It is reported so the owner can make that determination. The underlying fact — sensitive intelligence returned with no authentication — is confirmed regardless of how the tier boundary is ultimately defined.

Description

The premium intelligence endpoint (/api/<intel-report>) returns detailed analysis — wallet analysis, advanced threat signals and funding-source tracing — without requiring an Authorization header. The platform's public feature comparison presents these as paid-tier capabilities, and the authenticated free-tier profile (/api/<user-profile>) reports its premium-feature flag as false, yet the same class of data is served to anonymous callers.

Reproduction

  1. Issue an unauthenticated request to the endpoint: 
    curl -s "https://target.example/api/<intel-report>?asset=<ASSET-ID>"
  2. Observe a full intelligence response is returned with no Authorization header.
  3. Compare with the authenticated free-tier profile, which reports its premium-feature flag as false: 
    curl -s "https://target.example/api/<user-profile>" -H "Authorization: Bearer <free_tier_token>"
  4. Note the anonymous response contains the premium groups (wallet analysis, advanced threat signals and funding tracing) that the free tier is not entitled to.

Data exposed without authentication

Limitation. No paid-tier account was available. The fields below were identified as paid/elite-tier capabilities from the platform's public marketing and feature-comparison pages; it could not be independently confirmed that the unauthenticated response exactly matches a paid subscriber's. The core issue — data returned with no authentication — is confirmed regardless.

Capability (paid-tier)DescriptionReturned unauthenticated?
Advanced threat signalsDeveloper-activity, treasury-activity and liquidity-lock detectionYes
Wallet analysisCreator/owner wallet analysis and risk scoringYes
Funding attributionDeployer funding-source tracingYes
Holder distributionToken holder count and distributionYes
Full risk analysisComplete risk scoring and indicatorsYes

Business impact

  • Revenue leakage. If the exposed fields are genuinely paid-tier, the entire subscription model can be bypassed — anyone obtains paid intelligence for free.
  • Intellectual-property exposure. Proprietary scoring output is accessible to competitors and scrapers at scale.
  • Unbounded harvesting. With no authentication there is no per-user attribution or throttling, permitting bulk extraction of the platform's core data product.

Remediation

See Section 6. In summary: require authentication on the intelligence endpoint, enforce subscription tier server-side (never rely on the front end to gate fields), and apply per-user API rate limiting.

VA-02

Broken Rate Limiting on Password Reset — Emails Dispatched Despite 429

High
CVSS v3.17.5 (High)
CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H
StatusConfirmed & validated
CWECWE-770 (Allocation of Resources Without Limits or Throttling); CWE-799 (Improper Control of Interaction Frequency)
OWASP Top 10 2021A04:2021 — Insecure Design
OWASP API 2023API4 — Unrestricted Resource Consumption
Affected assetPOST /api/<password-reset> (path generalized)

Description

The password-reset endpoint has rate-limiting logic: after repeated requests it returns a RATE_LIMITED error with retryAfterSeconds: 300. However, the rate-limit check does not block the underlying action. Every request — including those returning RATE_LIMITED — still queues and delivers a reset email to the target address. The error response and the email dispatch are decoupled: the limit is enforced only at the response layer while the job queue continues to accept and process requests. The rate limit is therefore cosmetic.

Evidence

Response after the threshold is crossed:

{ "error": "Rate limit exceeded", "code": "RATE_LIMITED", "retryAfterSeconds": 300 }
  • Every request, including those returning RATE_LIMITED, triggered a reset email to the target inbox.
  • No suppression of queue insertion occurs when the limit is breached.

Reproduction

  1. Establish a baseline with a single reset request: 
    curl -s -X POST https://target.example/api/<password-reset> \
  -H "Content-Type: application/json" \
  -d '{"email": "target@example.com"}'
  2. Send repeated requests in quick succession: 
    for i in $(seq 1 20); do
  curl -s -X POST https://target.example/api/<password-reset> \
    -H "Content-Type: application/json" \
    -d '{"email": "target@example.com"}'
  echo
done
  3. Observe that once the threshold is crossed the response body reports RATE_LIMITED, yet reset emails continue to arrive in the target inbox for every request sent.

Root cause

The rate-limit check occurs after the email job is enqueued, or the queue insertion executes before the rate-limit result is acted upon. The validation and the side-effect are not transactionally coupled.

Business impact

ImpactDescription
False sense of securityRate limiting appears to protect the endpoint while providing no actual protection
Direct financial costThe transactional email provider bills per message; a sustained attack drives real cost
Inbox flooding / harassmentAny registered user can be flooded with reset emails on demand
Sender-reputation damageHigh-volume dispatch degrades deliverability for legitimate mail
Operational disruptionRequires manual queue flushing to stop cost accrual and delivery

Remediation

See Section 6. In summary: enforce the limit before enqueuing, couple the error response to skipping the action, deduplicate pending reset jobs per address, and add a challenge (CAPTCHA) plus a queue-depth circuit breaker.

VA-03

Origin IP Exposure — Cloudflare Protections Bypassable

Medium
CVSS v3.16.5 (Medium)
CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:L
StatusConfirmed & validated
CWECWE-693 (Protection Mechanism Failure); CWE-200 (Exposure of Sensitive Information)
OWASP Top 10 2021A05:2021 — Security Misconfiguration
Affected assetProduction origin host (IP redacted)

Description

The origin server's IP address is publicly discoverable because the TLS certificate served directly on the origin is indexed in certificate-transparency logs and associated with the target domain. The origin also accepts direct inbound connections from any source IP rather than restricting traffic to Cloudflare's published ranges. An attacker can therefore address the origin directly with a Host: target.example header, bypassing Cloudflare's WAF, edge rate limiting, bot-management controls and Cloudflare-provided DDoS protection for any traffic sent directly to the origin. Network-layer protections offered by the hosting provider, if any, are outside the scope of this assessment and may still apply.

Severity context. Rated Medium: the exposed origin was observed to be a reverse-proxy tier (nginx) hosted on a public cloud VPS rather than the core application server, which limits direct exploitability. The finding is nonetheless confirmed and defeats the CDN security layer the platform relies on.

Scope justification. Scored S:U. Although the attack circumvents Cloudflare, the vulnerable component (the origin's network exposure) and the impacted component (the same origin and its application) fall under one security authority — the platform owner controls both the origin firewall and the CDN configuration. S:C is reserved for impact crossing into a different security authority, which bypassing one's own edge control does not satisfy.

Evidence

The origin certificate binds directly to the target domain, confirming the host. Ports 80 and 443 accept connections from any source, and the application responds normally to direct requests carrying the domain Host header.

Reproduction

  1. Confirm the origin responds directly, bypassing Cloudflare, by setting the Host header to the domain: 
    curl -sk -H "Host: target.example" \
  "https://<ORIGIN-IP>/api/<intel-report>?asset=<ASSET-ID>"
  2. Observe a normal response identical to one routed through Cloudflare.
  3. Verify no Cloudflare headers (CF-RAY, CF-Cache-Status) are present in the direct response: 
    curl -skI -H "Host: target.example" "https://<ORIGIN-IP>/" | grep -i "cf-"
  4. Confirm SSH (port 22) is reachable from an arbitrary source IP.

Business impact

ImpactDescription
WAF bypassAll Cloudflare WAF rules are ineffective against direct origin requests
Rate-limit bypassCDN-level rate limiting is circumvented entirely (compounding VA-01 and VA-02)
DDoS exposureThe origin is directly reachable, so Cloudflare's volumetric protections do not apply to that traffic
Bot-detection bypassCloudflare bot scoring and challenges do not apply to direct origin traffic
SSH exposurePort 22 is reachable from the internet with no apparent source restriction

Chaining note. VA-03 amplifies the other findings: any CDN-level control the owner might add to compensate for VA-01 or VA-02 (WAF rules, edge rate limiting, bot challenges) can be side-stepped while the origin remains directly reachable. VA-03 should therefore be remediated alongside, not after, the application-layer fixes.

Remediation

See Section 6. In summary: restrict origin inbound traffic to Cloudflare ranges, lock down SSH, replace the public origin certificate with a Cloudflare Origin CA certificate, and enable Authenticated Origin Pulls.

5Business Impact Assessment

The findings map onto three distinct business risks — revenue, cost and resilience — which is what elevates them above their individual technical severity for a commercial data platform.

Business riskDriven byConsequenceExposure
Revenue and IP protection VA-01 Paid-tier intelligence and proprietary scoring obtainable free and at scale, undermining the subscription model and competitive position High
Direct operating cost VA-02 Attacker-controlled, unbounded transactional email dispatch billed to the platform, with manual intervention required to stop it High
User trust and abuse VA-02 Any registered user can be weaponized as a flooding target; harassment vector and support burden Medium
Platform resilience VA-03 The CDN protection layer can be bypassed, exposing the origin to volumetric attack and neutralizing compensating edge controls Medium
Sender / brand reputation VA-02 High-volume dispatch degrades email deliverability for legitimate users Medium

The findings also interact. VA-03 removes the edge as a place to compensate for VA-01 and VA-02, and VA-01's lack of authentication removes per-user attribution that would otherwise make VA-02-style abuse traceable. The recommended sequencing in Section 6 accounts for this.

6.1 Access control (VA-01)

  • Authenticate first. Reject unauthenticated requests to the premium intelligence endpoint with 401 in middleware, before any data is fetched.
  • Enforce tier server-side. After authenticating, resolve the caller's active subscription and filter the response to the fields that tier is entitled to. Never rely on the front end to gate premium fields — front-end classification of a response as "deep" tier is not an access control.
  • Default deny. Free and unauthenticated requests should receive only basic risk indicators; the premium groups (wallet analysis, funding tracing, liquidity analysis and advanced threat detection) should require paid authorization.

6.2 Rate limiting (VA-02)

  • Check before acting. Validate and enforce the limit early in the request lifecycle, before any job is enqueued; if exceeded, return the error and exit without side effects. The response and the action must be coupled — returning RATE_LIMITED while still processing is a logic error, not a rate limit.
  • Deduplicate at the queue. Before enqueuing a reset job, skip insertion if a pending job already exists for that address.
  • Add friction. Require a CAPTCHA on the second and subsequent attempts within a session.
  • Circuit breaker. If reset-queue depth exceeds a threshold (e.g. 500 pending jobs), halt further enqueuing and raise an operations alert.

6.3 Origin exposure (VA-03)

  • Firewall the origin. Configure the host firewall to accept ports 80/443 only from Cloudflare's published IP ranges.
  • Lock down SSH. Restrict port 22 to known management IPs; consider a non-standard port or VPN-gated access.
  • Break the certificate link. Use a Cloudflare Origin CA certificate instead of a public certificate bound to the domain, so the origin cannot be fingerprinted via certificate-transparency logs.
  • Authenticated Origin Pulls. Require a Cloudflare client certificate at the origin so only proxied requests are accepted.
